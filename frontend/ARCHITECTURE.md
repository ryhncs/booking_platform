# Frontend architecture

A guide to how the React app is put together, written for someone who is
learning React. Read it top to bottom once, then use it as a map when you open
the code. Every file also has comments explaining its non-obvious decisions.

**Stack:** React 19 · Vite · Redux Toolkit + RTK Query · React Router ·
Vitest + React Testing Library + MSW · plain CSS. All JavaScript, no TypeScript.

---

## 1. Running it

```bash
docker compose up --build        # from the repo root: db, redis, django, worker, beat, frontend
# app:     http://localhost:5173
# API:     http://localhost:8000/api/docs/  (Swagger)
```

Inside `frontend/` (or via `docker compose run --rm frontend <cmd>`):

| Command | What it does |
| --- | --- |
| `npm run dev` | Vite dev server with hot reload on :5173 |
| `npm test` | run all tests once (`npm run test:watch` re-runs on save) |
| `npm run lint` | ESLint, warnings fail the run |
| `npm run build` | production build into `dist/` |
| `npm run check` | lint + test + build (what CI runs) |

From the repo root, `./check.sh` runs the backend **and** frontend checks in Docker.

## 2. Folder structure

The code is grouped **by feature** (auth, businesses, bookings, owner) rather
than by kind of file (all components here, all API calls there). When you work
on bookings, everything you need is in one folder.

```

├── vite.config.js              dev server, /api proxy to Django, test settings
├── eslint.config.js

    ├── App.jsx                 wraps everything in the Redux <Provider> and <BrowserRouter>

    ├── index.css               all styles (plain CSS, see §9)
    │

    │   ├── Status.jsx          <Loading />, <ErrorMessage />, <Empty />
    │   └── Pagination.jsx
    │

    │   │                       LoginPage, RegisterPage, ProtectedRoute, useCurrentUser

```

Tests live next to the code they test (`BookingPage.test.jsx` beside `BookingPage.jsx`).

## 3. The data flow: from a click to Django and back

Almost every page follows the same path. Here it is for "show free slots":

```
 BookingPage.jsx
   const availability = useGetAvailabilityQuery({ staff, service, date })
        │   1. a React hook generated by RTK Query
        ▼
 bookingsApi.js   getAvailability: query: (args) => `/availability/?staff=..`
        │   2. the endpoint definition turns args into a URL
        ▼
 apiSlice.js      createApi({ baseQuery: baseQueryWithReauth, ... })
        │   3. checks the cache: same args already loaded? → return it, no request
        ▼
 baseQuery.js     adds "Authorization: Bearer <token>", sends fetch('/api/...')
        │   4. on 401: refresh the token and retry (see §4)
        ▼
 Vite dev server  proxies /api/* → http://web:8000  (vite.config.js)
        │   5. same origin for the browser, so Django needs no CORS setup
        ▼
 Django (DRF)     /api/availability/ → JSON
        │
        ▲   6. the response is stored in the Redux store under state.api
        │   7. every component using that hook re-renders with the data
```

What the component gets back from a query hook:

| Field | Meaning |
| --- | --- |
| `data` | the response body, once it has arrived |
| `isLoading` | first load, nothing to show yet → render `<Loading />` |
| `isFetching` | any request in flight, including a refresh while old `data` is still shown |
| `error` | set if the request failed → render `<ErrorMessage error={error} />` |
| `refetch` | function to load it again (used by "Try again" buttons) |

Mutations (things that change data) return a pair instead:

```js
const [createBooking, { isLoading, error, reset }] = useCreateBookingMutation()
await createBooking(body).unwrap()   // unwrap(): throws on error, so try/catch works
```

**Why RTK Query instead of `useEffect` + `fetch`?** You'd have to write the
loading/error state, caching, de-duplication (two components asking for the
same thing → one request) and "refresh the list after I created something" by
hand on every page. RTK Query does all of that from a declaration.

**Why one `apiSlice` with `injectEndpoints`?** One cache and one auth-aware
base query for the whole app, but each feature keeps its endpoints in its own
folder (`features/bookings/bookingsApi.js` etc.).

## 4. How authentication works

The backend uses JWT (djangorestframework-simplejwt):

* **access token**: proves who you are on every request; expires after 15 min
* **refresh token**: lasts 7 days; can be traded for a new access token at `/api/auth/refresh/`

### Where they are kept

| Token | Stored in | Why |
| --- | --- | --- |
| access | Redux state only (memory) | short-lived; losing it on reload costs one refresh call |
| refresh | Redux state **and** `localStorage` | so a page reload keeps you logged in |

`features/auth/authSlice.js` holds both. Reducers must be pure (no side
effects), so writing to `localStorage` happens in `app/store.js`, which
subscribes to the store and mirrors the refresh token whenever it changes.

> Trade-off: JavaScript on the page can read `localStorage`, so an XSS bug
> could steal the refresh token. An `httpOnly` cookie avoids that but needs
> CSRF protection on the Django side. This project chose the simpler option;
> know the difference before copying it into something serious.

### Logging in

`LoginPage` calls the `login` mutation. Its `onQueryStarted` (in `authApi.js`)
waits for success and dispatches `credentialsReceived({ access, refresh })`.
From then on `baseQuery.js` adds the access token to every request.

### When the access token expires (or after a page reload)

```
 component        baseQueryWithReauth                    Django
    │  request ──────►  GET /api/bookings/  ───────────────►  401 (token expired)
    │                   │
    │                   │ anyone already refreshing?  ── yes ──► wait for that refresh
    │                   │ no: POST /api/auth/refresh/ { refresh } ─►  200 { access }
    │                   │ store the new access token
    │                   │ retry GET /api/bookings/  ────────────►  200
    │  ◄──────────────  data
```

Details worth noticing in `api/baseQuery.js`:

* **One refresh for many 401s.** If five requests fail at once, they share a
  single refresh promise (`refreshInFlight`) instead of firing five refreshes.
* **Already refreshed?** If the token changed while a request was in flight,
  it just retries with the new one.
* **No loops.** The retry happens once; `/auth/*` calls (login with a wrong
  password is a 401 too) never trigger a refresh.
* **Logout only when it's really over.** If the refresh token is rejected
  (401/400) the user is logged out. A network error or a 500 does *not* log
  you out.

### Logging out

`Layout` dispatches `loggedOut()`. `store.js` listens for that action and runs
`apiSlice.util.resetApiState()`, which deletes every cached response, so the
next person on this browser never sees the previous user's bookings.

### Protecting pages

`ProtectedRoute` is a *layout route* in `AppRoutes.jsx`: its child routes only
render (through `<Outlet />`) when there's a logged-in user.

1. No refresh token → `<Navigate to="/login" state={{ from: location }} />`.
   `LoginPage` sends you back to `from` after logging in.
2. Logged in → it loads `/api/me/` (via `useCurrentUser`) and shows a spinner meanwhile.
3. `role="owner"` → customers see an explanation instead of the page.

This is about user experience, not security: Django checks permissions on
every request no matter what the UI shows.

## 5. How the cache stays fresh: tags

RTK Query caches every response. **Tags** tell it when a cached response is out of date.

* A **query** says which data it contains: `providesTags`
* A **mutation** says which data it changed: `invalidatesTags`
* When a tag is invalidated, every *mounted* query that provided it
  **refetches automatically**. Cached queries no one is looking at are just
  marked stale and refetched when next used.

Tag types are declared once in `apiSlice.js`:
`Me, Business, Staff, Service, WorkingHours, Booking, Availability, Timezone`.

### List tags

Paginated lists provide one tag per item **plus** a `LIST` tag
(`listTags()` in `businessesApi.js`):

```js
providesTags: (result) => [
  ...result.results.map(({ id }) => ({ type: 'Booking', id })),
  { type: 'Booking', id: 'LIST' },
]
```

Why `LIST`? A brand-new booking isn't in any existing tag yet, so creating one
invalidates `{ type: 'Booking', id: 'LIST' }` to make every booking list reload.

### Who invalidates what

| Mutation | Invalidates | So that... |
| --- | --- | --- |
| `createBooking` (success) | `Booking LIST`, `Availability` | it appears in "My bookings"; its slot disappears |
| `createBooking` (**409**) | `Availability` | the slot list is re-loaded and shows what's really free |
| `confirmBooking`, `cancelBooking` | that `Booking`, `Booking LIST`, `Availability` | cards and lists update; a cancelled slot is free again |
| owner edits (staff, services, hours, business) | their type + `Availability` | changes show up everywhere, including free slots |

`invalidatesTags` can be a **function of the outcome**, which is how the 409
case works (`bookingsApi.js`):

```js
invalidatesTags: (result, error) => {
  if (result) return [{ type: 'Booking', id: 'LIST' }, 'Availability']
  if (error?.status === 409) return ['Availability']   // someone beat us to it
  return []
}
```

That is the whole "this slot was just taken → refresh the slots" feature:
`BookingPage` only shows the message and clears the selected slot; the
refetch happens because of this function. The backend keeps its own Redis
cache of slots and clears it on every booking change, so the refetch really
returns fresh data.

Two more cache settings you'll see:

* `keepUnusedDataFor: 30` on availability: free slots go stale fast, so a
  cached copy is thrown away 30s after the page stops using it (default 60s).
* `keepUnusedDataFor: 3600` on the timezone list, which never changes.

## 6. Times and timezones

The API stores times in UTC. A haircut at a salon in Tehran happens at Tehran
time, wherever the viewer is. So `utils/datetime.js` formats every time in the
**business's** timezone (`booking.business_timezone`, `business.timezone`)
with `Intl.DateTimeFormat`, never the browser's. Free slots arrive with their
offset (`2026-11-02T09:00:00+03:30`) and are sent back unchanged when booking,
so the exact instant reaches the server. Times use a 24-hour clock so they
read the same in every locale.

The owner's timezone dropdown is filled from `/api/timezones/`, the exact list
the backend validates against, instead of the browser's list (which can differ).

## 7. Errors

RTK Query never throws inside components; it gives you an `error` object.
`utils/errors.js` turns it into text:

* `{ status: 'FETCH_ERROR' }` → "Can't reach the server…"
* `{ status: 500 }` → "Something went wrong on our side…"
* `{ data: { detail } }` → the server's message
* `{ data: { email: ['...'] } }` → field errors, shown next to the input (`fieldErrors`)

Booking errors carry a stable `code` from the backend. `bookingErrors.js`
switches on the **code** (`slot_unavailable`, `outside_working_hours`,
`invalid_request`), not on the English text, so wording can change safely.

Every data-loading component renders the same three non-happy states from
`components/Status.jsx`: `<Loading />` (`role="status"`), `<ErrorMessage />`
(`role="alert"`, optional "Try again") and `<Empty />`.

## 8. Testing

**Vitest** runs the tests, **React Testing Library** renders components and
finds things the way a user would (by role, label, text), and **MSW** (Mock
Service Worker) intercepts `fetch` and answers with fake API responses, so the
real store, real RTK Query and real `baseQuery` run in every test.

* `test/server.js`: the MSW server. Each test registers handlers with `server.use(...)`.
  Unknown requests fail the test (`onUnhandledRequest: 'error'`).
* `test/render.jsx`: `renderWithProviders(ui, { route, preloadedState })` gives
  each test a **fresh store** and an in-memory router. `loggedIn` is a
  preloaded auth state.

What is covered, and where:

| Behaviour | Test file |
| --- | --- |
| 401 → refresh → retry; one refresh for parallel 401s; logout when refresh is rejected; no logout on network errors | `api/baseQuery.test.js` |
| ProtectedRoute redirects, return-to-page after login, revoked session, owner-only pages | `features/auth/ProtectedRoute.test.jsx` |
| Booking 409: friendly message, slots refetched, taken slot gone; other errors by code | `features/bookings/BookingPage.test.jsx` |
| Confirm/cancel/who-cancelled, filters, empty states | `MyBookingsPage.test.jsx`, `IncomingBookingsPage.test.jsx` |
| Owner forms: create business, field errors, hours overlap, 409 on delete | `features/owner/owner.test.jsx` |

The booking-list tests use a tiny **stateful** MSW backend: confirming really
changes what the next `GET /bookings/` returns. That way the test proves the
list refreshed because of tag invalidation, not because the test said so.

Lessons from making the tests reliable (all visible in the code):

* **Wait for the data you expect, not for the first thing that appears.** An
  error message can render before the refetched list arrives, and old results
  stay on screen while new ones load. Use `waitFor(() => expect(...))` for
  "this should eventually be gone".
* `waitForElementToBeRemoved` throws if the element is *already* gone, so it
  fails whenever the response is fast. Prefer `waitFor`.
* `findBy*` / `waitFor` time out after 3s here (`test/setup.js`) instead of the
  default 1s, because test files run in parallel on CI.

## 9. Styling

One stylesheet (`src/index.css`), no UI library. For a learning project that
keeps every style visible and the dependency list short. Colours are CSS
custom properties (`--primary`, ...). Layout uses flexbox/grid with
`flex-wrap` and `repeat(auto-fill, minmax(...))`, so pages adapt to phone
widths without many media queries.

## 10. Recipe: adding a page

1. **Endpoint**: add it to the feature's `*Api.js` with `injectEndpoints`;
   give queries `providesTags` and mutations `invalidatesTags`.
2. **Page**: a component in that feature folder. Call the generated hook and
   render loading / error / empty / data.
3. **Route**: add a `<Route>` in `AppRoutes.jsx`, inside `ProtectedRoute` (and
   the `role="owner"` group for owner pages); add a `NavLink` in `Layout.jsx` if needed.
4. **Test**: `renderWithProviders(undefined, { route: '/your-page', preloadedState: loggedIn })`
   with MSW handlers for the calls it makes.

## 11. Known limitations

* The refresh token lives in `localStorage` (see §4 for the trade-off).
* `BookingCard` reads the clock once when it mounts to decide whether a hold
  has expired; if it expires while the page stays open, confirming fails with
  the server's "hold has expired" message instead.
* Staff, services and working-hours lists load only the first page (50 items).
* No optimistic updates: the UI waits for the server before showing a change,
  which keeps the cache logic easy to follow at the cost of a short delay.
